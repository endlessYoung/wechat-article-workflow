# 从 0 到 1：这个项目是怎么用 DSH 做出来的

> 一句话：重点不是「AI 生成」，而是「怎么把 AI 用起来」——从第一个 prompt 到可发布的 Skill，每一步的取舍和踩坑，比产出本身更有价值。

## 完整 road（关键节点 × 用了什么能力）

| 阶段 | 关键节点 | 用了 DeepSeek Harness 的什么 |
| --- | --- | --- |
| 1. 起步 | 直接甩需求，不寒暄 | 标准模式 + 完整工具链（文件读写 / Shell / 检索） |
| 2. 发现旧项目 | 目录里已有同名项目，定位冲突 | 澄清式提问（ask_user_question），给选项而非默认覆盖 |
| 3. 需求落地 | 一个需求 → 9 步任务清单 | 自主任务规划（todo list），逐项推进 |
| 4. 写码自测 | 列表解析 bug，自己定位修复 | 工具闭环：边写边跑测试，失败即回归 |
| 5. 连续迭代 | 加引用模块、换 Anthropic 风主题 | 多轮追加需求，每轮都能接住并落地 |
| 6. 无视觉读图 | 模型读不了截图 | 子代理尝试 → 失败后 OCR 兜底 |
| 7. 发布 | 图床 + 一键复制 + 长截图 | 后台任务 + 无头浏览器（puppeteer）+ GitHub API |

## 怎么更好地「用 AI」：几条可复用的实践

1. **先让它干活，别急着聊架构**：一个真实任务会逼出框架的全部关键机制。
2. **把需求拆到它能接住**：大需求拆成可验证的小步骤，用任务清单跟踪。
3. **关键节点敢拍板**：它停下来问的时候，给出明确取舍（比如「删除旧项目重建」）。
4. **让它边做边测**：别一次性梭哈，让它在每个阶段都有测试兜底、能自我修复。
5. **多轮迭代比一次到位更靠谱**：先跑通最小版，再一轮轮加需求、换风格。
6. **遇到能力边界就换工具链**：模型没视觉，就上 OCR；要截图，就上无头浏览器。

## 结论

「是不是 AI 写的」是伪命题；「怎么把 AI 用起来、怎么一步步把它领到对的方向」才是真功夫。这个仓库本身就是这套方法的产物。
